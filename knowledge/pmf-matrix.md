# PMF 生存检查表（pmf-matrix）

> 用法：在七问审计之后，用本表做系统性补盲。七问回答"凭什么收钱"，本表回答"能不能活下去"。
> 每个维度给出：结论（1-2 句）+ 证据标记（[代码证实] / [用户提供] / [待验证]）。
> 与七问重复的维度（价值主张、痛点、停用损失）直接引用七问结论，不重复分析。

## 检查维度

| # | 维度 | 关键问题 | 证据主要来源 | 常见死因 |
|---|------|----------|--------------|----------|
| 1 | 价值主张 | 为什么选你？独特收益能否一句话说清（含数量：省一半时间/漏检率降到 X）？ | 七问 Q1-Q3 结论 | 只说"用了 AI"，说不出收益数字 |
| 2 | 目标用户与场景 | 精确到什么角色、什么场景下用？（"跨境电商运营做投放计划时"，而非"所有电商"） | facts + 用户自身数据（只读聚合，见隐私红线） | 人群泛化，谁都能用 = 谁都不非用不可 |
| 3 | 差异化与壁垒 | 和替代方案比好在哪？能否被轻易复制？ | 七问 Q5 + 代码（领域逻辑深度） | 壁垒只有"先做了两个月" |
| 4 | 商业模式 | 谁付费？订阅/按量/席位/打包？免费与付费墙怎么切？ | facts + 代码（计费痕迹） | 定价盯着 Token 成本而非节省的人力；强弱功能打包整卖，支点被稀释 |
| 5 | 获取渠道 | 目标用户如何知道你并试用？（应用市场/SEO/社区/B 端销售/平台集成） | facts + [待验证] | 做完才想渠道，CAC 失控；推广前未确认行为数据会被记录（顺序应为采集就绪→推广）；多渠道同时推无法归因 |
| 6 | 核心指标 | 用什么数据判断产品活着且在成长？（留存、付费转化、复购、NPS） | facts + 代码（指标计算口径） | 只看注册数；口径失真（"任意请求=活跃"类虚荣指标，需读计算代码核实）；分析所需数据正被轮转/硬删 |
| 7 | 数据来源与质量 | 系统靠什么数据运行？合法、稳定、够新吗？ | 代码（数据获取/外部依赖） | 爬来的数据、随时会被断供的第三方 API |
| 8 | 合规与安全 | 隐私、版权、行业监管（GDPR/医疗/金融）、AI 输出风险如何满足？ | 代码 + facts | 合规是上线后才想的事 |
| 9 | 体验与可用性 | 非技术用户能否上手？结果可理解、可控、可回退吗？ | 代码（界面/错误处理/解释性输出） | 需要读文档才能用的"效率工具" |
| 10 | 成本结构与扩展性 | 算力/人工/获客成本可控吗？用户翻十倍撑得住吗？有无缓存/批处理/降级？ | 代码（架构、缓存层） | 推理成本随用户线性涨且无优化手段 |
| 11 | 团队与迭代能力 | 团队能否持续迭代与运维？关键角色齐吗？ | facts | 单人项目做需要持续运营的产品 |
| 12 | 反馈闭环 | 有无机制让系统越用越好？（反馈入口、日志分析、数据沉淀） | 代码（反馈/埋点/沉淀机制） | 产品发布即巅峰，没有飞轮 |

## 飞轮检查（最后一问）

画出这个项目的理想飞轮并检查每一环是否存在：

```
用户更多 → 反馈/数据更多 → 产品更聪明好用 → 留存更高 → 盈利更多 → 投入更多研发 → 用户更多
```

- 逐环标记：已存在 [代码证实] / 有计划 [用户提供] / 缺失 [待验证]
- 缺失最多的一环，就是 backlog 里"沉淀物"类改动的方向。

## 输出要求

- 12 个维度逐条给结论，禁止跳过；无信息的维度明确写"[待验证] + 建议的验证动作"，不许编。
- 挑出 **3 个最薄弱维度**，进入报告的"风险"小节，并对应到 backlog 或 facts 待补充项。
