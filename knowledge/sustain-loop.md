# 核心逻辑提炼、持久盈利运转与用户观测就绪（sustain-loop）

> 用法：七问回答"凭什么收钱"，PMF 表回答"能不能活下去"，本文回答两件更具体的事：
> (A) 这个项目到底在做什么、钱在哪一步；能不能**持久盈利运转**（不是一次性卖掉）；
> (B) 项目负责人**看不看得到用户在用什么**——看不到，前面一切建议都无法被验证。
> 输出进入报告第 1 节（A-1）与第 3 节（A-2、B）。

## A-1 核心逻辑提炼（报告第 1 节末尾，先于七问）

从代码（不是 README 宣传）提炼，按顺序读：入口（main/路由/命令注册）→ 核心流程编排 → 持久化/沉淀物。
输出固定四行，每行必须挂 [代码证实 路径]：

1. **一句话核心逻辑**："为 <谁> 把 <输入> 变成 <输出>，替他承担 <哪段麻烦>"。
   禁止用"基于 AI 的智能 XX 平台"这类能力描述；必须是麻烦描述。
2. **价值链路**：`输入（来自哪）→ 处理（关键判断在哪个文件）→ 输出（谁消费）→ 沉淀（留下什么）`。
   沉淀一格为空时显式写"无沉淀"——这是 Q3/Q5 最常见的根因。
3. **钱在哪一步**：链路中哪一格是用户愿意付费的那一格（通常是"处理"里的判断，或"沉淀"的积累），
   其余格是成本。若付费格与开发重心（画像"提交目录热度"）不一致，指出定位漂移。
4. **靠人硬撑的原状**：没有它，这段链路由谁用什么工具手工完成（对应 Q1；能从代码推断的写推断并标"推测"）。

## A-2 持久盈利运转模型（报告第 3 节；红灯项目省略）

"能收一次钱"和"能一直收钱"是两回事。逐环检查以下五环，每环：结论 + [代码证实]/[用户提供]/[联网检索]/[待验证]。

| 环 | 关键问题 | 证据来源 | 常见断点 |
|---|---|---|---|
| 收入循环 | 付费**重复触发**的事件是什么（每月账单/每次交易/每个新项目/续期）？还是一次性买断？ | 代码计费逻辑、facts 第 4 节 | 只有买断，没有重复触发事件；"订阅"但用户一个月只用一次 |
| 留存循环 | 用户回来的理由是沉淀物（档案/历史/数据）还是习惯？停用后沉淀物能否带走？ | 代码持久化层、A-1 沉淀格 | 沉淀物可一键导出且无增量价值 → 随时可走 |
| 成本结构 | 每个活跃用户的边际成本（推理/算力/人工客服）是否随收入等比或更慢增长？有无缓存/批处理/降级？ | 代码外部 API 调用、缓存层 | 每次使用都调大模型全量推理，无缓存无蒸馏 |
| 获取渠道 | 新用户从哪来，成本是否随规模下降（口碑/SEO/平台集成 vs 人肉销售）？ | facts 第 3 节、README、联网检索 | 单靠创始人个人渠道 |
| 壁垒累积 | 每多一个用户/每多用一次，产品是否变得更难被替代（数据/模板/规则/集成）？ | 代码反馈/沉淀机制、Q5 | 使用不产生任何积累 |

联网检索（占 8 次预算中的 2 次，只采权威来源、附 URL 与访问日期）：
- 检索 1：同类产品当前主流盈利模式与价格带（官网 pricing 页优先），用作收入循环与定价锚的**基准**，不是结论。
- 检索 2：该品类近 12 个月的显著变化（大厂免费化/平台内置/监管），用作成本结构或渠道的风险输入。
- 检索失败 → 对应环退回 [待验证]，不编造。

输出："持久盈利运转模型"小节 = 五环表 + **最弱一环**（一句话）+ 修复最弱一环的**零代码验证动作**
（遵守处方纪律 1：先问用户/取数，再改代码）。最弱一环的动作进入 backlog。

## B 用户观测就绪（报告第 3 节；分级来自画像"观测/统计信号"，不得自行改级）

> 目的：让负责人**知道用户用了哪些模块**。没有这个，七问里所有"[待验证]"永远验证不了，
> 处方纪律 8 的"报告价值=增量"也无从核销。

### B-1 分级解读（画像已确定性给出 0-3 级，审计只做解读与核实）

- **0 无**：盲飞。任何"用户喜欢 X 模块"的判断都是猜。
- **1 仅系统观测**（错误监控/指标/日志）：知道系统活着，不知道用户活着。
  例外：若日志含用户标识 + 路由/命令名且保留期 ≥ 30 天，可用"一次性日志聚合"替代埋点（读码核实保留策略，处方纪律 5）。
- **2 有 SDK 无模块事件**：只有 PV/会话，不知道哪个功能被用、哪个从没人碰。
- **3 有事件上报**：读码核实三件事——事件名是否对应**功能模块**（而非泛"click"）、是否带用户/会话标识、
  数据落在哪里能否被负责人查看。任一不满足降为 2 级解读。

### B-2 与处方纪律 2 的边界（必须遵守）

- 允许且要求：**最小事件集采集就绪**（3-5 个事件，一天内可接完）——它是"采集就绪 → 推广"的前置条件，
  不是看板体系；没有它，推广后的读数为零，浪费唯一的冷启动机会。
- 仍然禁止：小样本（活跃 <100）阶段建议看板体系、多维分析平台、数据仓库、A/B 实验系统。

### B-3 最小事件集（按项目实际模块命名，不给泛化名）

1. `activated`：完成一次核心链路（A-1 的"处理"格跑通一次），带首次/非首次标记
2. `module_used{module}`：每个功能模块的入口各打一次，module 取值 = 项目真实模块名（列出 3-8 个）
3. `core_output_consumed`：输出被消费（导出/复制/分享/下游调用），证明不是打开看看
4. `paywall_hit` / `upgrade_clicked`：仅当代码存在付费墙时
5. 可选 `returned`：距上次使用 ≥ 1 天的再次 `activated`（用于 Q3 停用损失读数）

每个事件必须附**落点文件**（[代码证实] 路径：入口函数/路由/命令注册处），不附路径不列。

### B-4 工具推荐矩阵（按技术栈 × 用户地域，两套都给但标明主推；地域先看 facts"主要用户地域"，
空则按代码/README/文案语言与依赖源推断并标"推测"）

| 形态 | 主要用户在中国大陆 | 主要用户在海外 | 零依赖兜底 |
|---|---|---|---|
| Web 前端 | 百度统计（免费，事件 API `_hmt.push(['_trackEvent',...])`）；自托管 Umami（数据不出境、免费）；神策/GrowingIO（企业级，付费） | GA4（免费，gtag event）；Plausible（隐私友好，付费/自托管）；PostHog（事件+漏斗，免费额度大） | 前端 `fetch` POST 到自家后端一张 `events` 表 |
| 后端/API | 自建：请求日志带 `user_id + route`，每日一条 SQL 聚合到快照表（不依赖第三方） | PostHog server SDK；Segment（贵，早期不推） | 中间件计数写数据库/Redis HyperLogLog |
| CLI/桌面/插件 | 自建 HTTPS POST（opt-in，字段白名单）；Aptabase（桌面友好） | PostHog capture API（HTTPS POST 即可，无需 SDK）；Aptabase | 本地 JSONL 计数 + 用户手动 `stats` 命令上报 |
| 移动 App | 友盟（免费）；神策 | Firebase Analytics（免费） | — |
| 微信小程序 | 微信自带"小程序数据分析"（自定义事件免费）；友盟小程序版 | — | — |

选型三条硬规则：
1. **隐私红线**：默认 opt-in 或至少显式告知；字段白名单公示；不采集内容与个人信息。工具自身合规
   （大陆用户数据是否出境）优先于功能强弱。
2. **一天接完**：推荐方案的接入量 ≤ 1 天；超过的降级为"先自建一张事件表"。
3. **负责人能看**：给出负责人**查看的具体方式**（后台哪个页面 / 一条 SQL），看不到等于没接。

### B-5 输出要求（报告第 3 节"用户观测现状与建议"小节）

- 现状：分级 + 一句解读 + 命中的工具/文件（引用画像）
- 分级 ≥ 2 且事件对应模块：写"已就绪"，只列缺失的事件（若有）
- 分级 < 2 或事件不对应模块：给 **最小事件集表**（事件名 / 触发含义 / 落点文件）+ **推荐工具**（主推 1 个
  + 备选 1 个 + 理由，含地域与隐私判断）+ **负责人查看方式**
- 强制产出一条 backlog：类型=代码，标题"最小事件集采集就绪（<主推工具>）"，
  已有真实流量/即将推广 → P0；尚无流量 → P1（须在首次推广前完成）。已有条目沿用旧 ID。
- 红灯项目：本小节只写现状分级一行，不给接入建议（先转向，再谈观测）。
