# 价值审计七问（value-judgment）

> 用法：审计时逐条回答七问。每条结论必须挂靠证据（代码文件/目录、facts 条目、README 内容）；
> 无证据的结论必须显式标记为"推测"。禁止编造数据。

## 三条底层判断（判断力来源）

1. **用户不是为"能力"付钱，而是想少承担一段麻烦。**
   演示功能（读取、整理、生成）不构成付费理由；替客户承担一段工作、少漏掉一个可能造成损失的问题，才构成。
2. **先找一条正在靠人硬撑的流程，而不是研究技术还能做什么。**
   客户正在用 Excel、微信群、几个人手动倒腾的流程，机会真实；客户"本来就不做"的事，收费通常很难。
3. **能不能赚钱，看客户停用以后会损失什么。**
   停用后问题立刻回来（每天多花几小时、遗漏的风险重现），才有持续付费。
   定价参考节省的人力与避免的损失，不是 Token/算力成本。

## 审计七问

### Q1 替代前提：没有这个产品之前，用户怎么完成这件事？
- 绿灯：正在用 Excel / 微信群 / 邮件 / 人肉流程硬撑，且有具体场景描述
- 黄灯：说不清现状，或现状是"用竞品凑合"（转入差异化审计）
- **红灯：他本来就不做这件事** → 触发整体红灯
- 证据来源：facts（用户现状）、README 场景描述

### Q2 颗粒度：它承担的是一个小动作，还是一段来回切换、容易出错的流程？
- 绿灯：替代一段需要人来回切换多个工具/角色、容易出错的完整流程（判断→查证→整理→决策准备）
- 黄灯：只替代单个小动作（写一封邮件、格式转换），省几分钟
- 证据来源：代码的功能边界（入口/流程编排代码覆盖了流程的哪几段）

### Q3 停用损失：停用后第二天，谁会痛？痛在哪？折算多少人力/损失？
- 绿灯：能说出具体的人、具体的痛（每天多 N 小时 / 某类风险重现），且可折算金额
- 黄灯：有人不方便，但绕得过去
- **红灯：没人痛，用不用都不影响工作**（"有用户、没收入"型产品）→ 触发整体红灯
- 证据来源：facts（停用损失描述）、代码中是否存在"沉淀物"（数据积累、历史档案、工作流依赖）

### Q4 付费方：谁付钱？付费理由是省下的人力，还是避免的损失？
- 绿灯：付费方明确，且付费理由可用"人力成本 × 时间"或"损失概率 × 金额"表达
- 黄灯：用的人和付钱的人不是同一个，且尚未打通采购逻辑
- 红灯：说不出谁会付钱
- 证据来源：facts（付费方、定价）、代码中是否有计费/订阅/席位/配额痕迹

### Q5 防复制：差异化能否被一个周末 demo 复制？
- 绿灯：有数据积累、行业知识库、工作流嵌入深度或渠道等结构性壁垒
- 黄灯：当前领先靠先发和打磨，无结构性壁垒（可接受，但要有积累壁垒的路线）
- 证据来源：代码中的数据飞轮机制（反馈收集、标注、历史沉淀）、领域逻辑的深度

### Q6 致命项：数据来源、合规、成本结构有没有一票否决的问题？
- 检查：训练/运行数据是否合法稳定；隐私与行业合规（GDPR、医疗、金融）；
  推理/算力成本是否随用户线性增长且无优化手段（缓存、批处理、蒸馏）
- 任一项存在且无解 → 降一档灯色并列为最高优先级风险
- 证据来源：代码（数据获取方式、外部 API 依赖、缓存层）、facts（合规场景）

### Q7 改动方向：现有代码里，哪三处改动能让它"开始对结果负责"？
- 这是从审计到 backlog 的桥梁。寻找"展示能力 → 承担结果"的改造点，典型模式：
  - 从"输出信息"升级为"输出判断 + 依据 + 下一步动作"（发现异常、标记偏高、准备追问清单）
  - 从"单点功能"升级为"覆盖流程闭环"（过滤→查证→整理→只留一次人工确认）
  - 增加"沉淀物"（档案、历史对比、数据积累），制造停用损失
- 证据来源：代码结构（现有能力盘点）+ Q2/Q3 的缺口

## 整体灯色判定规则

- **红灯**：Q1 答案为"本来就不做"，或 Q3 答案为"没人痛"。
  红灯时报告不生成商业建议/backlog/路演问答稿，改为输出"转向建议"（2-3 个：同样的技术能力可切入哪些"正在靠人硬撑"的场景）。
- **黄灯**：Q1-Q4 中任意一条只有黄灯答案，或关键结论缺乏证据支撑。
- **绿灯**：Q1-Q4 均有扎实答案，且至少一半结论有代码或 facts 证据。
- 灯色判定必须给出一句话理由，引用触发条款（如"红灯：Q3 停用无损失"）。
